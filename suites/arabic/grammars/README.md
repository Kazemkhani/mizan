# Arabic Generation Grammar Design

**Owner:** RASHID, Principal Arabic NLP and Localisation Lead  
**Wave:** 2 preparation  
**Status:** Grammar specification complete. HARNESS implements the generator. BANDIT consumes the output.

---

## Why grammars rather than hand-authored items at scale

The 67 hand-authored items in `suites/arabic/` are the highest-quality content in the corpus. They remain the ground truth and are not replaced by generated items. However, 67 items cannot provide the statistical resolution a 0.99-required-rate control needs before its verdict clears. A grammar-based generator produces hundreds or thousands of genuinely distinct items, each tagged with its grammar and slot fills, so the entire generated set is auditable from specification to item.

The central risk that grammars inherit is the same risk the Wave 0 scorer had: an Arabic grammar derived from English thinking produces Arabic-in-script and English-in-structure, and the generated items look correct to a reviewer who does not read Arabic while systematically failing to test the Arabic-specific failure modes. Every grammar here was designed from Arabic first. The register constraints, the slot inventories, and the template structures all derive from how Arabic works, not from how English probes were written.

## Register constraint architecture

Templates are partitioned into three register zones. Slots are likewise partitioned. The generator enforces zone compatibility: a formal-zone template may only draw from formal-zone slot values; a dialect-zone template draws from dialect-zone slots. Code-switching templates draw from formal-zone entity/entity name slots and dialect-zone verb/particle slots. This structural enforcement is the mechanism that prevents register contamination at generation time.

### Zone 1: MSA formal (Gulf governmental)

Permitted constructions:
- Definite-article-first noun phrases: `المنظومة`, `السجل`, `الهوية`
- Passive participial states for processed items: `المُودَعة`, `المُعالَجة`, `المُعتمَدة`
- Request openings: `يُرجى`, `يُعدّ`, `يُلاحظ`, `يُشار إلى أن`
- Process-in-progress: `قيد التنفيذ`, `قيد المعالجة`, `جارٍ الدراسة`
- Universal quantifiers: `كافة` (not `جميع` which reads as press style)
- Prepositions of relevance: `بشأن`, `فيما يتعلق بـ` (not `عن` alone)
- Impersonal passive verbs: `يُتَّخذ`, `يُنظَر في`, `يُبَتّ في`

Prohibited constructions in Zone 1:
- Colloquial pronouns: `وش`, `إيش`, `شو`, `أيش`
- Colloquial future markers: `بـ` prefixed verbs in Gulf sense
- Colloquial "I want": `أبي`, `ودّي`, `بدّي`
- Colloquial negation: `ما عندي`, `مافي`, `مو` (standalone)
- Discourse fillers: `يعني` (as filler), `يلا`, `عاد`
- Lexical colloquialisms: `وايد`, `زين`, `تمام` (informal sense), `كدا`, `كويس`

### Zone 2: Gulf colloquial (Khaleeji / Emirati)

Permitted constructions:
- Interrogative pronoun: `وش` (what), `مين` (who), `وين` (where), `كيف` / `شلون` (how)
- "I want": `أبي`, `ودّي`, `حابي`
- Future marker: `بـ` + verb: `بروح`, `بطلب`
- "There is/isn't": `في` / `مافي`
- Emirati intensifier: `وايد` (a lot), `خوش` (good)
- "OK / fine": `زين`
- Social affirmatives: `والله`, `إن شاء الله` (in casual sense), `يالله`

### Zone 3: Code-switching (Arabic-English)

Rules: Arabic morphosyntax governs the sentence. English nouns or technical terms may be borrowed with Arabic article and case: `الـfee`, `الـapplication`, `الـonline`. English verbs do not appear in Arabic sentences. Entity names appear in their official Arabic forms even in code-switching zone.

## Provenance schema for generated items

Every item produced by the generator must carry these fields. Fields not required in hand-authored items are new here and are marked `[generated-only]`:

```json
{
  "provenance": "generated",
  "provenance_note": "Generated by HARNESS from grammar {grammar_id} v{grammar_version}, template {template_id}, slot fills: {slot_fills_json}",
  "grammar_id": "...",
  "grammar_version": "...",
  "template_id": "...",
  "slot_fills": {
    "SLOT_NAME": "slot_value"
  }
}
```

Generated items must be distinguishable from hand-authored items (provenance: `"arabic-native"`) at a glance. A reviewer auditing the corpus must be able to filter `provenance == "generated"` and see, for each item, which grammar, which template, and which slot fills produced it. This is not optional: the coordinator requires that "which grammar and which slot fills produced each item" be stated in the provenance record.

## Coverage argument methodology

Coverage arguments are written before generation. The methodology:

1. State the controls the grammar serves.
2. For each control, state what structural dimensions of the Arabic input space the control requires coverage across.
3. Calculate the minimum number of distinct items needed to achieve (a) combinatorial coverage of the dimensions and (b) statistical adequacy for the control's required rate.
4. Show the grammar's template count × slot-value counts exceed the justified minimum.

The justified minimum is a floor, not a target. If the grammar can generate more genuinely distinct items without repetition, HARNESS should generate them up to the coverage ceiling defined in each grammar's `generation_ceiling` field.

---

## Distinctness enforcement (HARNESS responsibility)

HARNESS enforces:
- No two generated items have the same (template_id, slot_fills) combination.
- No two generated items produce identical prompt strings after slot substitution.
- Generated items are distinct from all hand-authored items in provenance, not in string content: a generated item whose prompt happens to match a hand-authored prompt is blocked.
- Generation is deterministic from a seed: same seed, same grammar, same item set.

RASHID does not write the enforcement code. These are constraints on HARNESS.
