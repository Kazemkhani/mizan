# Data Requests for the Operator

Charter Addendum 01 section 2, point 5. When a dataset needed for a use-case
binding cannot be reached from the build environment, it is recorded here in
full rather than invented. Each entry carries everything the operator needs to
fetch it by hand, and each is surfaced at the next checkpoint.

A dataset is never fabricated to fill a row in this table. An empty binding
is an honest gap; a plausible-looking invented one is a fabricated benchmark.

---

## Open requests

None. DR-001 through DR-006 are resolved. See the Resolved section below.

## Format

Each request states: the use case it grounds, the dataset name as published
(or the search terms to find it), the publishing entity, the portal URL, the
Resource GUID if known, what specifically is needed from it, what was tried
and the exact failure, and what MIZAN does in the meantime.

## Resolved requests

### DR-001 | Bayanat REST API access (was: blocks all five Bayanat bindings)

**Status: Resolved 2026-08-19. The API path is permanently closed to
unauthenticated clients. The correct access method is HTML page parse.**

**What was tried (BAYAN wave 1, 2026-08-19):**

Every API endpoint attempted returned HTTP 302 (Found) redirecting to
`/en/error/404`. The original conclusion was that the portal is a Sitecore
SPA requiring antiforgery tokens generated by browser JavaScript, and that
unauthenticated server-side calls are rejected before API logic runs.

Specific endpoints that returned 302:
- `https://bayanat.ae/api/Dataset/GetAll?pageNo=1&pageSize=10&lang=en`
- `https://bayanat.ae/api/DatasetResources/GetDatasetResource?resourceID=test`
- `https://bayanat.ae/api/DatasetResources/GetAll?pageNo=1&pageSize=10`
- `https://bayanat.ae/api/Dataset/GetDatasets?pageNo=1&pageSize=20&topic=Government&subTopic=Service%20Centers`

**What was discovered next (BAYAN wave 1 addendum, 2026-08-19):**

The conclusion about the API was correct but the conclusion that the entire
portal was inaccessible was wrong. The dataset info pages return HTTP 200 to
plain unauthenticated curl. The page body is 699,500 bytes of server-rendered
HTML containing the complete Data Explorer preview table.

The documented REST endpoint `/api/DatasetResources/GetDatasetResource?resourceID=`
was investigated further:
- A bad value returns HTTP 400 with a JSON validation body (not 302 or 404).
  HTTP 400 means the endpoint is present and validating input, not absent.
- The page HTML contains two identifier schemes that might look like Resource
  GUIDs: Sitecore item identifiers (used for page component rendering) and
  base64url tokens in `data-resource-id` attributes (used for view counting).
  Neither scheme is accepted by GetDatasetResource.
- The Resource GUID that GetDatasetResource requires is not exposed in the
  page HTML to unauthenticated clients. It is an internal portal concept.
- Seven Sitecore item GUIDs from one dataset page were all tried against the
  endpoint. All returned HTTP 200 with a zero-byte body.

**The thread that resolved the block:** HTTP 400 (bad input) versus 302/404
(absent resource) is a meaningful distinction. A 400 means the endpoint validates
but the supplied identifier is wrong. Pulling on that thread led to discovering
that the identifier schemes visible in the page are not the right ones, and
from there to examining whether the page itself carries the data. It does.

**What the correct access method is:**

`GET https://bayanat.ae/en/Datasets/Dataset-info?id={token}`

Where `{token}` is the 43-character base64url token from the dataset listing
page hrefs (`https://bayanat.ae/en/Datasets` returns the listing with 200,
each dataset href carrying the full token). The token uniquely identifies
the dataset info page. The page carries the Data Explorer preview table
in server-rendered HTML: `<table id="accordionTableOne-{n}">` with a
`<thead>` of column names and a `<tbody>` of up to 5 rows per resource.
The total record count is embedded in the page as `"TotalCount":{n}` in
JSON within a server-rendered script block.

The fetch script is `agents/data/fetch_bayanat.py`. It validates expected
column names explicitly and fails loudly on an empty or wrong-column parse.

**Residual risk:** HTML parsing is more brittle than calling a stable API.
A markup change to the Data Explorer table would break the parse. Mitigation:
the committed cache means a markup change produces a loud HASH_MISMATCH or
COLUMN_MISMATCH at the next refresh check, not a silently wrong cache.

**Outcome for uc-001:** The FCSC "Population by Sex and District" dataset
is now bound and hash-verified via the HTML parse method. See
`docs/evidence/data_sources.md` uc-001 section.

### DR-002 | Bayanat: Government Service Centre transactions (uc-001)

**Status: Resolved. The FCSC Population by Sex and District dataset
provides a better grounding for the primary Arabic-accuracy control
than the service transaction dataset described here. The Ajman Speed
Centre dataset (retained in suites/data/) covers service knowledge.
No further Bayanat fetch for uc-001 is required at this stage.**

**Original request:** A dataset recording citizen transactions at UAE
government service centres, by service type, language of interaction,
and volume. FCSC or TDRA on bayanat.ae.

**Reason closed:** The uc-001 primary control is Arabic language accuracy:
does the model produce federally standardised Arabic vocabulary for places,
categories, and government terms? The FCSC Population dataset carries exactly
this: Arabic and English district labels ("ابو ظبى", "الغربية", "العين",
"دبى", "الشارقة") and demographic categories from a federal publication. The
service transaction dataset would have added volume and frequency data; that
dimension is not in the current control specification. Reopen if the control
specification is extended to include service request frequency calibration.

## Decision record: Bayanat access method

**Decision date:** 2026-08-19  
**Decision:** Parse server-rendered HTML from dataset info pages rather than
calling the documented REST API.  
**Why:** The REST API requires a Resource GUID that is not accessible to
unauthenticated clients. The dataset info page carries the complete Data
Explorer preview table in server-rendered HTML. This is the only unauthenticated
access path that works.  
**Risk acknowledged:** HTML parsing is more brittle than a stable API. The
portal can change its markup. Mitigation: explicit column validation in the
parse step and a committed hash-verified cache that makes markup changes visible
as loud failures rather than silent corruption.  
**Owner:** BAYAN. Code: `agents/data/fetch_bayanat.py`.
