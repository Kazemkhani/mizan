# MIZAN project charter

## Purpose

MIZAN is a research prototype for evaluating AI models against the controls of a
specific government use case. It combines a model registry, an adaptive
evaluation engine, an append-only evidence record and a bilingual certificate.

The project exists to answer a narrow question: can an assurance team reach a
defensible model decision with less testing than an exhaustive run, without
hiding which evidence was collected, which controls remain uncertain or which
assumptions shaped the result?

## Intended users

The primary users are AI assurance, procurement and governance teams evaluating
models before deployment in public services. Researchers and engineers can also
use the repository to inspect the allocation, stopping and evidence mechanisms.

MIZAN is not an authority and does not represent endorsement by a UAE government
entity. A certificate produced by this prototype is an evaluation artefact, not
a legal approval or regulatory certification.

## Product contract

A complete MIZAN evaluation must preserve this chain:

1. A model is registered with its declared capabilities, intended use and model
   card.
2. The selected use case determines which controls and evidence types apply.
3. The adaptive engine chooses the next probe according to its recorded state
   and stopping rules.
4. Every probe, response, score and decision is written to an append-only,
   hash-chained evidence record.
5. The certificate reports the result per control, links it to the evidence and
   states the evidence tier actually earned.

No interface, report or certificate may imply a stronger result than this chain
supports.

## Non-negotiable principles

### Arabic is first-class

Arabic evaluation is not an English translation pass. Arabic-native suites,
attack cases, interface copy and certificate content are maintained as distinct
assets. Right-to-left behaviour is part of acceptance, not a later visual task.

### Evidence outranks assertion

Quantitative claims must be generated by committed scripts, attributed to a
named source or labelled as assumptions. A result without a reproducible path is
not a result MIZAN publishes.

### Uncertainty remains visible

A control decided by a statistical bound is not presented as equivalent to one
that merely reached its probe budget. Missing evidence, stale data and
unresolved controls remain visible to the operator and on the resulting
artefacts.

### Determinism is a feature

The default demonstration path runs offline with deterministic model adapters,
committed suites and self-hosted assets. Retries must not conceal unstable
evaluation behaviour.

### Human accountability remains outside the model

MIZAN organises evidence for a human decision. It does not replace legal review,
security review, procurement authority or accountable human judgement.

## Current scope

The prototype includes:

- a FastAPI registry and evaluation API;
- a UCB1 allocator with per-control stopping rules;
- deterministic endpoint adapters and reproducible evaluation suites;
- append-only evidence enforced by database triggers and a hash chain;
- controls and use cases grounded in published UAE material and open data;
- Arabic-native evaluation content and a bilingual React interface;
- generated bilingual certificates with per-control evidence detail; and
- automated test, language, contrast, grounding and evidence gates.

## Explicitly outside the current scope

The current repository does not claim:

- production identity, access control or tenant isolation;
- deployment-grade key management or externally verifiable certificate
  signatures;
- legal interpretation of UAE regulation;
- exhaustive coverage of a model, language, sector or threat class;
- independent validation by a regulator or certification body;
- live model safety beyond the probes that were actually executed; or
- automated model training or remediation.

These are release boundaries, not footnotes. Work that changes one of them must
update the risks, architecture and roadmap in the same pull request.

## Engineering governance

- Consequential technical choices are recorded in
  [`DECISIONS.md`](DECISIONS.md), including alternatives rejected.
- Known limits and their mitigations are maintained in [`RISKS.md`](RISKS.md).
- Changes enter through pull requests and must pass the required checks on the
  current default branch.
- Security reports follow [`../SECURITY.md`](../SECURITY.md) and must not begin
  in a public issue.
- Public claims follow the language and grounding gates in `scripts/audit/`.
- Historical role-based build reports are retained as engineering provenance,
  with their status explained in [`PROVENANCE.md`](PROVENANCE.md).

## Release standard

A release is credible only when:

1. the Python suite and interface build pass from the committed lockfiles;
2. register, grounding, contrast and evidence gates pass;
3. the adaptive and exhaustive paths are compared under identical decision
   rules and an identical corpus;
4. known statistical, security and data limits are stated where a reviewer can
   see them;
5. the English and Arabic paths have been reviewed at the same release state;
6. no unresolved critical security finding is known; and
7. a clean checkout can reproduce the documented demonstration and proof.

The implementation sequence and remaining production work are tracked in
[`ROADMAP.md`](ROADMAP.md).

## Participation

Contributions are welcome when they improve validity, traceability, Arabic
quality, security or reproducibility. Start with
[`../CONTRIBUTING.md`](../CONTRIBUTING.md), and include evidence proportionate to
the claim the change introduces.
